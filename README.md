
# 改测审改绿（写代码全局固定流程）

用户拍板（2026-08-03）：**所有写代码任务**（不限项目/语言）必须走 改→测→审→改→绿 循环，直到审核无 critical/major + 对比全绿才部署。

**⚠️ 循环次数不限**：③审→④改 反复进行，直到某轮只剩误报/无新问题才进 ⑤绿。没有"固定 5 轮"的说法（client-x 实际 7 轮才交付）。轮数由问题数量决定，不设上限。

**🔀 收敛规则（2026-08-04 评审建议，已采纳）**："次数不限" ≠ "无限打磨"：
- 连续 2~3 轮无实质改动（或只剩风格/优化类意见）→ 停
- 续循环入场券：只接受**正确性/安全/性能**三类硬问题；风格、优化类意见不构成再开一轮的理由（记入待办，不阻塞交付）
- 每轮记录改动量，用于判断是否收敛

## 循环五步

```
① 改(+git) → ② 测 → ③ 审 → ④ 改(+git) → ⑤ 绿 (重复 ③④ 直到无新问题)
```

**🔀 三回路嵌套模型（2026-09-11 用户确认）**：5步法不是单一循环，而是三个嵌套回路，任一未闭环不算绿：

| 回路 | 速度 | 触发 | 职责 |
|---|---|---|---|
| 测↔改（快） | 快 | 测试失败 | 快速反馈，改一下测一下 |
| 审↔改（慢） | 慢 | 审核发现 critical/major | 质量把关，再审带已修清单 |
| 改→回归测（中） | 中 | 每次改动 | 修复不搞坏别的（含审核轮修出的）+ 重新验证基线 |

**核心纪律：④改 之后必须回 ②测 重跑回归**——无论改动来自测试失败还是审核意见，三个回路共享这条。缺一号回路的典型症状：启动审核但交付时无“审核结果→修复→再审确认”闭环记录，bug 漏到用户手上（某内部项目 2026-09-11 实证：两个 UI bug 漏到生产）。

### ① 改（含 git，用户 2026-08-16 强化）
- **每次代码修改必须推本地 git**（绝不只用目录拷贝备份）：
  1. 无 git 仓库 → 先 `git init` + .gitignore + 首次 commit 建基线
  2. 改前：`git add -A && git commit` 备份原始版本（替代 .bak 文件）
  3. 本地改代码（遵守各项目代码同步铁律：先 scp 拉最新 → 本地改 → 语法检查 → diff 确认 → 上传）
  4. 改后：`git add -A && git commit` 记录修改
  5. `git diff` 核对只改了该改的行
- 一次只改一个根因，不做 drive-by 重构

### ② 测（"测试导出结果"是固定环节，不是可选项）
- **⚠️ 测什么必须先按框架定范围，不是凭感觉（2026-09-12 挂接）**：每个改动按「测试策略决策框架」三维度列测试范围（改动影响面→路径枚举①主②错③边界④并发⑤交互组合⑥回归→正确方法表），先列成 TESTING.md（方法+预期+状态）再动手，不是 bug 补集。框架细节 → 见 knowledge/测试策略决策框架-2026-09-12.md（权威源，技能内不复制）
- **⚠️ 测的标准不确定时，必须先问用户确认测试标准再动手**（测什么范围/对比什么/什么算通过——不自己猜。例：对比哪些订单、是否含图片、数值容差、zip 顺序是否算差异）
- **UI 功能铁律（2026-08-27 用户拍板）：凡有用户界面的功能，必须用无头浏览器真实测试**（CDP 驱动 chrome-headless-shell 真实填写/点击/截图），不能用 curl 模拟 POST 代替——curl 只能验证服务端逻辑，验证不了 JS 分步交互/前端校验/弹窗/渲染。详见 references/headless-ui-testing.md
- **curl 查到字段在 DOM 里 ≠ UI 测试（2026-09-11 教训）**：只验证渲染不验证交互——预览写库、二次上传残留两个 bug 都是用户上手后才报出，因为交付前没做按钮点击/表单交互真实测试。
- **按钮 action URL 生成函数必须真实点击验证，curl 手动拼 URL 测端点会掩盖漏参（2026-09-13 实测）**：重构参数化 `action_url(extra)` 后调用点漏传动作参数 → 点击只是无检查重载页面，用户当场发现"点了没变"。原因 = 测试时手动拼了完整 URL curl 端点（200 全过），完全绕过生成函数。规范：参数化/重构后**真实点击按钮**断言 location.href 含动作参数（如 `xxx=1`）+ 服务端结果时间戳变化；curl 只能测"端点本身"不能测"生成链路"。
- **⚠️ UI 全路径测试前置，不是等用户点名（2026-09-11 用户要求固化）**：UI 功能交付前默认测全操作路径+错误分支——上传/预览/二次上传/取消/错误文件/确认弹窗/DB 落库/按钮 type 默认行为。测试矩阵先于代码列全写入 TESTING.md（方法+预期+状态），不是 bug 补集。
- **UI 通用坑（2026-09-11 实证）**：表单内 execute/提交类按钮必须显式 `type="button"` 防默认 submit 行为（预览阶段误触发写库）；二次上传预览区必须先清空重置（残留上一次数据）；JS 多次改动必须 bump 版本号防浏览器缓存旧 JS。
- **⚠️ 按钮 name/value 坑（2026-09-12 内部项目实证，全通用）**：`<button type="submit" name="btn">` 提交时 value 默认空串，后端 `!empty($_POST['btn'])` 恒 false → 保存永久失效(表单 POST 200 但永不保存，毫无提示)。规范：①按钮显式 `value="1"` ②后端用 `isset()` 而非 `empty()` ③UI 全路径测试必须真实鼠标点击(JS `form.submit()` 不携带按钮 name/value)。详见《插件开发规范》§4
- **实际调用/运行验证**：全端点 curl / 运行测试，确认 200 + 产物完整可读
- **与旧版输出对比**（有原版必对比）：
  - PHP 原版可能藏在**本地副本**（`www/data/www/html/{站}/wp-content/plugins/`）或服务器**不同文件名**（实测：原版可能是 `*_exc.php` 等非预期名，不能只按预期名找）——先 `ls *exc*.php` + 本地副本，md5 核对
  - 对比纪律见下方"对比要点"
- 回归：之前验证过的基线（如 13 单 0 差异）必须重跑确认没改坏

### ③ 审（**固定用本机 OpenCode**，用户 2026-08-21 拍板）
- **审核执行 = 动态调用 `multi-model-code-review` 技能（唯一权威源，09-06 版）**：不在此处复制矩阵内容——模型分工/命令/坑/FT 分界/凭据扫描全部以该技能为准，执行前 skill_view(name='multi-model-code-review') 加载最新版。
  - 当前生效矩阵（详细见 multi-model-code-review）：**云端主模型（DeepSeek Flash 官方直连）× 2 路 + 本地自托管模型（FreeToken 35B，统一出口）× 2 路 = 4 路必跑**（代码审核 + 测试视角各两路）；云端增强路（Pro）暂停中。2026-09-18 起云端两路对齐主模型；本地两路 2026-09-22 起统一走「统一出口」（后端模型切换对客户端透明）。
  - **执行形态（2026-09-18/20 固化）**：① 内嵌模式——单文件/少量文件时把全文内嵌进 prompt（省读取、绕权限、防游走），各路题面同一形状；② 单 wrapper 发车——全部路包在一个后台 wrapper 里、只等一次完成通知；③ 本地后端并发纪律——同一后端任一时刻只处理 1 个生成，本地两路**顺序**发，勿并发饿死。
  - **沙箱纪律（2026-09-15/20 实测）**：OpenCode 只能读写工作目录，目录外路径触发 auto-reject，且 **auto-reject 会静默杀死整个会话**（无报错、进程消失）——参考文件预放进项目目录（如 `core-refs/`），题面写「沙箱须知」。
  - **条件式判定（2026-09-20 实战）**：reviewer 给"修复 X 或书面接受残余即视为无 Critical/Major"时——把残余**逐条书面化接受**（理由 + 去向）即判收敛；口头飘过不算。
- 代码审查环节固定使用本机 OpenCode CLI（不换其他审查工具/不跳过）
- **收敛判定**：所有模型都明确输出"无 critical/major，可收敛" = 绿（6 轮收敛实录：R1 30 问题 → R6 全绿）
- 按模块分批并行审（1-2 文件/批），一次全量会挂死
- prompt 必须带**上一轮已修清单**（"第一轮已修复: X/Y/Z。请验证修复是否正确(有无遗漏/新bug)"）——否则 AI 重复报已修问题
- 要求：中文输出、Severity critical/major/minor + 行号 + 修复建议、只审不改
- **审核执行注意**：--variant 合法值只有 high/max/minimal（无 xhigh）；prompt 用 $(cat file) 传入避免转义；审核快照目录必须完整（含 require 依赖文件）


### ④ 改（同 ①，每处修改走 git：改前 commit → 改 → 改后 commit）
- 修 critical/major；minor 评估后决定
- **误报判定三件套**：`grep 该符号`（0 匹配）+ `go build`/编译（通过）+ `git diff`（确认改动）——都过就是 AI 误报（读到中途旧文件快照），不盲改
- **理论建议 vs 实证冲突**：AI 报"排序缺 tiebreak/价格取首个变体不对"等理论问题时，若与旧版导出已 0 差异 = 行为符合原版，**以实证为准不改**，加注释说明原因防后人误改
- **AI 理论发现（拼写/字段名）以官方离线文档为权威源裁决，生产日志 code:0 ≠ 字段名正确**（project-b 案例 2026-08-16 → 2026-09-07 反转修正）：曾判 `outer_goos_id` 为正确字段名（凭生产日志 code:0/is_success:true），该结论已被 2026-09 离线 API 文档实锤推翻——官方字段是 `outer_goods_id`，网关**宽容忽略未知字段**，code:0 只代表网关收到请求，不代表 OMS 正确解析。教训：① 字段名正确性查 project-b-official 离线 API 文档（权威字段源），不靠日志假象 ② AI 拼写疑点是线索不是结论，但反驳它必须有文档级证据，日志 code:0 不够

### ⑤ 绿（终止条件）
- **⚠️ 部署前先过「交付前清单」（2026-09-12 挂接）**：版本衬空/CHANGELOG/git/缓存清理/基线复验/审核闭环/维护记录三步, 逐项勾选, 一项不过不交付。清单详情 → knowledge/交付前清单-2026-09-12.md（权威源）
- 某轮只剩误报/无新问题 → 终止
- 全部修复部署后跑最终回归（全端点 + 数据对比基线）→ 全绿才交付
- **⚠️ 交付总结必须附审核结果清单（2026-09-11 固化）**：不得只写“全部完成”——必须列出审核发现问题数（critical/major/minor）、已修复项、再审确认、回归基线复验（重跑原已通过的基线）。五步法启动而未附闭环记录 = 未真正走到绿

## 对比要点

| 场景 | 做法 |
|------|------|
| Excel 类 | 与旧版同批导出，Python zipfile + sharedStrings **逐单元格对比**（数值归一化 `801.0`==`801`） |
| PDF 类 | PyMuPDF 提取文本，`款号\|SKU` **双标签**正则提产品序（老/新模板标签不同，单标签误报）+ 总计区对比 |
| 排序差异 | 先确认原版是否排序、按什么排序（usort/uasort/插入序）——**每个导出格式独立查源码**，不能跨格式复用排序代码 |
| zip 顺序 | Go 并发导出完成序不定 → 按请求 ids 顺序收集输出（map[oid] + 按 ids 遍历） |
| 对比必须同批跑 | PHP→Go 连续导出，排除订单时间差伪差异 |

## 验证纪律（2026-08-22 用户拍板固化，全 Agent 通用）

1. **复制/生成/部署任何文件后必须验证存在**：`ls -la <path>` + `file <path>`（或服务器 md5），不验证不交付。违反示例：2026-08-22 两次误报 xlsx 生成成功（实际 venv 未建、文件从未生成——工具结果不可见时假设成功）。
2. **工具输出不可见（Result unavailable）时绝不假设成功**：不编造"已确认"结论——重跑命令或用可见方式（本地 terminal 直接跑）验证。
3. **验证基于真实可见输出，不是"应该成功"的推断**；汇报时区分「我看到了什么」vs「我假设了什么」。
4. 部署后验证三件套（rsync/git/scp 同理）：文件存在 → 内容正确（md5/php -l/node --check）→ 运行效果（curl/回归）。

## 关键坑

- **测试必须用真实页面生成的数据**（2026-08-18 实战）：手工构造的 id/nonce 会掩盖真实格式问题——`uniqid('x', true)` 带小数点（`x123.456`）与 ID 白名单正则冲突、被 Sizzle 解析成 class，真实页面 AJAX 全挂而手工 id 测试全绿。AJAX/动态内容测试一律从页面 HTML 提取真实参数再发请求
- **uniqid(true) 带小数点**：拼 JS 选择器/进白名单正则前必须 `str_replace('.', '', ...)`（保熵 + 兼容两全），不能简单去掉 more_entropy（同微秒多实例重复 id）
- **nopriv AJAX nonce 对匿名用户公开**（不绑定会话，GET 页面即得）→ 服务端参数校验不能依赖 nonce 兜底：`$_POST` 数组参数（`id[]=x`）在 PHP8 下对 `preg_match/sanitize_key` 抛 TypeError 500，必须 `(string)` 强转后再校验
- **review 运行期间不要改文件**——AI 读启动时快照，中途修改导致误报（project-a 实测：报"headerRow 编译阻断"实际已删，grep 0 匹配 + build 通过 = 误报）
- **opencode→本地模型 输出为空 + exit 0 = 本地代理流式转发 bug**（2026-08-31 实测）：代理层原为"全量缓冲后转发"（读完再写），opencode 的 openai-compatible SDK 走 SSE 期望实时 chunk → 解析失败空输出。已修为**流式透传**（边读边写 + flush + `Connection: close`）。**排查法**：opencode 直连后端 OK vs 走代理空 → 定位到代理层；本地模型是 reasoning 模型，思考 token 要足（max_tokens 1000 才出 content，100 只出 reasoning）
- **修复后必须全局 grep 同类模式**：修了 1 处路径穿越，还要 grep `uploads/" +`、`os.ReadFile`、`base + ` 找漏网（logo/fallback 分支最容易漏）
- 安全修复类：修完 grep 确认全覆盖再进下一轮
- 测试文档（TESTING.md）随流程更新：每条测试 = 方法 + 预期 + 状态，执行后回填

## 交付物三清单（2026-09-08 用户拍板，引用形式）

任何多文件/多设置点的插件·主题·系统，发版/升级/卸载须守「三清单」：安装清单（标准产物开发时写清 + **例外追加**——非常规操作当场记账）/ 升级 delta（含废弃项移除段，防旧文件/旧定时任务残留）/ 卸载清单（反安装）。**升级第一问 = 保留数据还是不保留**：保留型（有 DB/options 设置）→ 兼容升级+增量迁移，禁止卸载重装（丢数据=事故），升级前仍走 4步法①备份；不保留型/纯文件 → 清旧装新。**⚠️卸载/清理前做所有权检查**：清单项分独占/共享，共享项（其他系统引用）先 grep 引用检查，有引用者不删只注明——避免过度删除。规范细则/类型落地/待办盘点 → 见 knowledge/自研交付物三清单规范-2026-09-08.md（权威源，技能内不复制细节）。
